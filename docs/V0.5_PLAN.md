# CCM v0.5 Plan

## 1. Purpose

This document is the operational plan for CCM v0.5. It mirrors the structure
of `docs/V0.4_PLAN.md`: scope boundaries, explicit non-goals, milestones,
risks, and owner decisions.

Read in this order:

1. [README.md](../README.md)
2. [docs/DESIGN.md](DESIGN.md)
3. [docs/V0.4_PLAN.md](V0.4_PLAN.md)
4. this file

Provenance: the five theme investigations, an adversarial fact-check, and a
cross-theme synthesis were produced on 2026-10-09 by a 7-agent design
workflow (5 investigators + 1 fact-checker + 1 synthesizer, run
`wf_1f76c0d2-6d8`) against main @ cf7e1ee. Roughly 150 file:line anchors
were verified by direct reads; the fact-check's corrections and the
synthesis's cross-theme decisions are already folded into the themes below
(section 7). Do not re-litigate settled decisions — see section 8.

## 2. Status

v0.4.0 was released 2026-10-03; its §11 backlog was fully dispositioned
2026-10-04 (three fixed, one do-not-fix, one verified-not-a-defect, one
cleared). The CI gate must stay green on every push to main.

Owner theme selection (2026-10-04) — the four v0.5 themes:

- adaptive routing — cost_weight derivation from real usage (scoped to
  advise-only; see §3.1 and §8.3)
- persistent session ids across restarts — the client→target mapping
  survives proxy restarts (`clients.toml`, not client-side stable ids)
- non-chat-completions endpoints + OTLP export — investigated as ONE theme;
  the endpoint half resolved to Anthropic-side auxiliary endpoints
  (`count_tokens` forwarding, conditional `/v1/models` synthesis), because
  Claude Code only ever speaks Anthropic protocol to the proxy (§3.3)
- provider discovery / gateway capability probing

Owner greenlight (2026-10-09): "execute per the recommendations" — every
§8.3 open decision resolved per its recommendation (recorded in §8.1), the
§8.2 registered defaults stand, and milestone execution began. M0 is
complete (§5); its outcome drops the `/v1/models` synthesized route (never
observed) and confirms both externally-gated premises.

Explicitly deferred (not selected, dispositions in §11): remote control
authentication (still requires a design first), UI/TUI, reverse translation.

## 3. Themes

### 3.1 Adaptive routing, advise-only (`ccm advise`)

Problem: `cost_weight` is a hand-entered prior (`DESIGN.md:157-162` —
"static user-provided metadata … not measured billing or benchmark values";
the starter ships glm=0.25 / claude=1.0 by fiat, `config.rs:124`). v0.4 M6
already records per-request four-way tokens, a pricing snapshot, and
`cost_usd` into `usage.jsonl` — the data is in hand, but no tool tells the
owner how far their hand-entered weights drifted from realized spend, or
what to change them to.

Mechanism:

- New top-level `ccm advise` (new module `src/advise.rs`; dispatch in
  `main.rs`; the `ccm history` subcommands stay raw dumps, advise is
  analysis with flags `--window` / `--min-samples` / `--model`).
- Data path: `history::read_usage(dir, since=now-window)`
  (`history.rs:876+`, bounded scan) → a RECOMPUTE fold: per-model realized
  USD = Σ(tokens/1e6 × **current** `[models.<name>.pricing]`) over complete
  records only. NOT `aggregate_costs` verbatim — that sums the embedded
  record snapshots (`usage.rs:205-208`), which mixes price regions across a
  price-table edit; the shared piece is the per-model fold, and a recompute
  variant is built instead (synthesis correction, §7).
- Output per model: analyzed requests (complete + priced), realized
  USD/request, current static `cost_weight`, suggested value, plus a
  pasteable TOML fragment. Both per-request and per-token columns with an
  explicit cross-provider tokenizer caveat (token counts come from each
  provider's own usage frames, `usage.rs:12-26` — per-token numbers are not
  comparable across protocol families).
- Honesty rails, all printed never written: `ccm advise` NEVER writes
  config; unpriced models print `cost unknown — never guessed` (the
  `aggregate_costs` unpriced language, `usage.rs:157-159`); below
  `--min-samples` (default 20 — cost variance is far larger than success
  rate's, so higher than `HEALTH_MIN_SAMPLES=3`, `select.rs:15`) prints
  `insufficient — unchanged`; selection bias (usage only records what was
  actually routed) and not-bill-truth are stated in USAGE.
- `quality_weight` stays manual — there is no honest derivation path from
  proxy-visible signals (success rate already feeds reliability;
  `complete:false` is a disconnect, not quality; no ground truth exists).
- The derivation is a pure function (records + current pricing →
  suggestions) so a future runtime variant can reuse it verbatim.

### 3.2 Persistent client sessions (`clients.toml`)

Problem: one proxy serves many long-lived Claude Code sessions; the
sessions routinely outlive the proxy (upgrade, crash, reboot). On restart
every scoped entry is wiped (`proxy.rs:146-160` starts from an empty
HashMap; the doc comment at `proxy.rs:53-57` pins in-memory-only as
invariant 8), and still-running sessions — which keep sending their
launch-time-fixed `CCM_CLIENT_ID` — silently fall back to the global
target: requests keep succeeding, on the wrong model. Recovery is manual
re-switching per session.

Mechanism:

- New `$CCM_HOME/clients.toml`, written ONLY by the proxy. Per entry:
  `id` (charset-validated at load, `[A-Za-z0-9._-]{1,64}`,
  `proxy.rs:233-246`), `target`, `last_seen_ms`. `requests` is intentionally
  NOT persisted — `usage.jsonl` is the durable ledger; the convenience
  counter resets to 0 on restart (documented).
- Write hooks: (1) in `apply_switch`'s scoped branch after the map update
  (`api.rs:707-716`; sync IO in the control handler is precedented —
  `apply_switch` already loads config.toml synchronously at `api.rs:705`);
  (2) a periodic refresh task reusing the metrics-snapshot-task shape
  (`proxy.rs:166-184`): every N secs rewrite the file snapshotting the
  map's CURRENT state. The task persists traffic-bumped `last_seen_ms`
  values UNCHANGED — it never stamps now() (that would make the TTL dead
  code; synthesis correction, §7, pinned by test). Idle-skip when the map
  is empty; no exit-time write (no graceful shutdown, same honesty as M5).
- Load at startup in `serve()`, mirroring the AppState load
  (`proxy.rs:95-99`): each target revalidated against current config —
  stale/unresolvable entries dropped with one warning naming them;
  corrupt/torn file → warn + empty map, degrading to exactly v0.4 behavior
  (the history downgrade pattern, `proxy.rs:123-131`); one startup line
  with the restored-entry count.
- Eviction ships WITH persistence (restarts used to be the GC): LRU cap on
  `last_seen_ms` at insert (default 256) + TTL dropping entries older than
  7 days at load. Retires the V0.4 §11 per-client-quota/LRU trigger.
- Atomic write: tmp-file + rename, with a Windows rename-over-existing unit
  test (the repo's rotation code only ever renames to fresh names,
  `history.rs:588-589` — the overwrite path is unexercised here).
- Config: top-level `[clients]` section (`persist = true` default,
  `ttl_days = 7`, `max_entries = 256`), serde defaults, read once at
  startup. `persist = false` restores v0.4 memory-only semantics byte for
  byte.
- Invariant 8 is reworded (the DESIGN.md:780 owner call, §8.3): `ccm
  switch` stays runtime-only for the GLOBAL target; scoped client entries
  persist best-effort in `clients.toml` — never `state.toml`, never
  credentials. Invariant 9 is untouched and pinned by test (`state.toml`
  byte-identical across scoped switch + restart).
- Boundary statements: two proxies on one `CCM_HOME` = last-writer-wins on
  `clients.toml` (the scenario is already degraded for history,
  `history.rs:24-28`); persisted lines contain no credential material
  (test, mirroring `history.rs:1487`); restored-but-forgotten targets are
  the new failure mode — mitigated by the startup line, `ccm clients`
  gaining `last_seen` in its CLI row (the API already returns it,
  `api.rs:655-668`), and the short-ish TTL.
- Client-side stable ids (`x-ccm-session` semantics) are explicitly NOT in
  scope: `--client` / `CCM_CLIENT_ID` already provide opt-in stability
  (USAGE.md:330, 409), and a third identity channel adds precedence rules
  for little gain. Deferred, §11.

### 3.3 Auxiliary endpoints (`count_tokens`, conditional `/v1/models`)

Problem: the launcher hands Claude Code `ANTHROPIC_BASE_URL=<proxy>`
(`launcher.rs:90-93`), so Claude Code treats the proxy as the full
Anthropic API — but the router serves only `/v1/messages` plus the control
plane (`api.rs:215-240`); no fallback is registered, so every other path
hits axum's default 404 with an empty body. `POST
/v1/messages/count_tokens` 404s today; USAGE.md:341 documents "Claude Code
tolerates it" as author-tested. The assumed cost — that Claude Code falls
back to a local token approximation, drifting the context-remaining meter
and auto-compaction timing on long sessions — is the M0 gate (§5, §8.3):
the repo cannot test client behavior.

Scope note (owner-visible reframe, §8.3): the backlog named
"non-chat-completions OpenAI endpoints" — but Claude Code never sends
OpenAI-protocol requests to the proxy, so OpenAI-side endpoint expansion
(embeddings, images, audio, files, rerank) has no client. The real gap is
Anthropic-side auxiliary endpoints. `count_tokens` is the one with an
established user problem; `GET /v1/models` is conditional.

Mechanism:

- Register `.route("/v1/messages/count_tokens", post(...))` in
  `control_router`. Handler: 405 for non-POST (mirror `proxy.rs:292-294`);
  client identity from headers as usual, but a SIDE-EFFECT-FREE target
  read — the entry's `requests` counter and `last_seen_ms` are NOT bumped
  (one shared decision with §3.2: counters and last_seen stay
  generation-driven; fork the read helper off `resolve_request_target`,
  `proxy.rs:269-289`); config load + route resolution; PRIMARY model only
  (single attempt — a count is only meaningful for the model that will
  actually serve generation).
- Anthropic kinds (`anthropic` / `anthropic-compatible`): rewrite the
  `model` field (`rewrite_model`, `proxy.rs:1043-1051`, protocol-agnostic —
  mandatory, since Claude Code sends the placeholder `ccm`,
  `launcher.rs:91`), forward to `base_url + kind.count_tokens_path()` (new
  accessor beside `upstream_path()`, `provider.rs:63-71`, returning
  `/v1/messages/count_tokens` for anthropic kinds and `None` for openai),
  inject credentials via `copy_request_headers` + `apply_auth`
  (`proxy.rs:1053-1076`), dedicated 10s timeout (counting is fast; the
  shared proxy client has NO timeout at all, `proxy.rs:147`), pass status +
  body through unchanged. An upstream gateway that lacks the endpoint
  answers itself — byte-identical to today's client experience.
- `openai-compatible` primary: 404 with an Anthropic error envelope
  (reuse the `translation_failure_body` shape, `proxy.rs:918-926`) naming
  the boundary — 404, not 501, because 404 is the status Claude Code
  demonstrably already tolerates. No upstream call, no local estimate
  (a confidently wrong count from the wrong tokenizer is worse than a 404;
  the `translate.rs` precedent is honest refusals, not approximations).
- ZERO routing/observability side effects: no circuit reads or writes, no
  metrics, no decision/trace ring, no usage capture (a count body has no
  `usage` object — wrapping it would record zeros against a nonexistent
  decision id), no Prometheus, no history. Pinned by before/after
  bit-identical assertions on all of those maps. Boundary documented:
  count traffic is invisible to every metric family — an SRE dashboard will
  under-count requests vs upstream bills; also restated in the OTLP docs
  (§3.5).
- `GET /v1/models` (was Option D, conditional on M0): **M0 observed the
  client never calling it** across all flows — the route is dropped, the
  404 stays, and USAGE documents both it and the tolerated
  `HEAD /api/hello` startup probe M0 discovered.
- Stub-gateway boundary (M0 finding): z.ai implements count_tokens as a
  stub returning `input_tokens: 0` for any input; minimax counts for
  real. Passthrough means the gateway's answer is the answer — a zero
  count is indistinguishable from a legal empty-input count, so the proxy
  passes it through and MAY warn once on stderr when a 0 count answers a
  large request body (M3 design note). Documented in USAGE beside the
  primary-tokenizer caveat.

### 3.4 Provider discovery (`ccm discover`)

Problem: onboarding a new gateway is three manual steps (`ccm add provider`
→ `ccm auth set` → per-model `ccm add model`), with `model_id` copied by
hand from the gateway's docs/console (the USAGE.md:181-198 minimax
example). A copied-wrong id only surfaces at `ccm health`. Worse, gateway
capability pits (which ids actually work, which force thinking, which
parameters are silently dropped) are discovered by hitting them in
production — the MiniMax notes at USAGE.md:847-848 are hand-learned prose.

Mechanism:

- New `ccm discover [provider]` subcommand (read-only until confirmed):
  credential via `credential::get` (missing key → the existing env-name +
  `auth set` message), `GET {base_url}/v1/models` with kind-appropriate
  auth (`apply_auth`; anthropic kinds add `anthropic-version`, the
  `health.rs:30-35` pattern), 10s timeout on a fresh client, lenient
  parsing of both protocol shapes (the common skeleton is `data[].id`;
  anthropic adds `has_more` pagination, capped at 10 pages; openai adds
  `object:"list"`/`owned_by` for display). Pagination fields are OPTIONAL
  — M0's live calibration: z.ai omits has_more/first_id/last_id entirely
  while minimax returns the full anthropic list shape.
- Registration: interactive multi-select (the `manage.rs:122-138` stdin
  style — no TUI dependency) or `--all` for scripts (the documented
  non-interactive path, USAGE.md:210 precedent). Alias = normalized
  model_id (non-`[A-Za-z0-9_-]` → `-`, suffix on collision); routing
  weights default 1.0/1.0; `pricing = None` per the hand-entered-prices
  policy (`config.rs:113-115`). KEY difference from `add model` upsert:
  an already-registered `(provider, model_id)` is SKIPPED with a notice —
  never overwritten (protects hand-tuned weights; pinned by test).
- Hand-off to §3.1: discovery prints a commented `[models.<alias>.pricing]`
  skeleton for each selected model — the journey is discover → hand-enter
  prices → `ccm advise` becomes useful; advise's unpriced message names
  the config edit (no pricing CLI flag exists, by policy, `manage.rs:60-62`).
- Shape/kind cross-check (nearly free, catches today's costliest config
  error early): an anthropic-shaped response against a declared
  `openai-compatible` kind (or vice versa) warns.
- Degradation paths pinned: 404/405 → "gateway does not expose /v1/models;
  add models manually" (non-zero exit); 401/403 → the health-style auth
  failure text; all requests time out. Honest boundary in docs: the
  gateway's list is a convenience, not a contract — listed ids can 400 at
  use time, working models can be unlisted. Chained-ccm boundary (a
  provider whose base_url points at another ccm): discovery lists that
  ccm's aliases as if they were gateway ids — documented, not blocked.
- doctor: the endpoint line (`doctor.rs:69-72`, currently an unauthenticated
  GET of `base_url` whose status "varies by gateway") upgrades to an
  unauthenticated `GET /v1/models` existence probe — making "does this
  gateway support discovery at all" (the theme's single biggest
  uncertainty: anthropic-compatible gateways may not implement the
  endpoint) an explicit, visible fact. `health.rs` gains the missing
  request timeout in the same change.
- `--probe` capability checks are a CONDITIONAL separate milestone (§5 M6,
  §8.3): one minimal request per probe (stream support via content-type of
  a `stream:true, max_tokens:1` ping — the repo already handles
  content-type divergence; usage reporting in the same ping;
  thinking-disablability for anthropic kinds), default OFF (probes spend
  real money and quota), results printed only — never persisted to the
  Model schema (point-in-time data goes stale in config). Anthropic's
  `/v1/models` capability fields (`max_input_tokens` etc. — there is no
  `context_window` field; map to `max_input_tokens`) are displayed for
  genuine Anthropic only, not persisted.

### 3.5 OTLP metrics export (hand-rolled OTLP/HTTP JSON)

Problem: ccm's runtime metrics have exactly two exits — local scrape
(`/metrics`, requires the user to run a Prometheus server) and disk JSONL.
An owner running a standard collector pipeline cannot ingest ccm's metrics
without standing up a server just for it. An OTLP push path (POST to a
collector, e.g. `http://localhost:4318`) lets ccm join the OpenTelemetry
ecosystem directly.

Mechanism:

- Option B (the dependency-discipline extension of `prometheus.rs`, whose
  existence reason is "no exporter crate"): a new `src/otlp.rs` mirroring
  the PromState/render split — a pure `render_otel(Snapshot)` plus config;
  the push loop is a `tokio::spawn` task in `serve()` beside the
  metrics-snapshot task (`proxy.rs:166-184` pattern). Zero new
  dependencies (serde_json + reqwest are already direct; the
  opentelemetry-crate alternative was measured at +31 net-new crates for
  spec insurance a 12-family cumulative-only exporter does not need).
- Config: `[observability.otlp]` — `endpoint` (required when the section is
  present), `interval_secs = 30` default; section absent = entirely off.
  Collector auth headers, if ever needed, come from the
  `OTEL_EXPORTER_OTLP_HEADERS` env var ONLY — never config.toml (the
  credentials invariant).
- Reuse, not a second source of truth: the Snapshot assembly currently
  inline in `control_metrics_exposition` (`api.rs:381-435`) is extracted
  into a shared fn used by both the handler and the loop. `PromState`
  construction is decoupled from `prometheus_enabled` (`proxy.rs:140-144`
  becomes `prometheus_enabled || otlp.is_some()`) while the `/metrics`
  route stays keyed on `prometheus_enabled` alone (`api.rs:235-238`) —
  OTLP-on + scrape-off keeps the route OFF. The three places asserting
  prom-presence == route-registration (`proxy.rs:73-76`, `api.rs:231-234`,
  DESIGN.md:371-375) are reworded in the same change.
- Wire format (spec-derived; ONE live otelcol smoke is the acceptance
  gate, §5 M0/M4): POST `{endpoint}/v1/metrics`, `application/json`,
  ExportMetricsServiceRequest with resource attributes `service.name=ccm`,
  `service.version`, `service.instance.id` (stable hash of CCM_HOME —
  distinguishes multiple CCM_HOMEs pushing to one collector). Counters →
  monotonic CUMULATIVE sums (int64 as JSON strings); gauges → asDouble;
  the two histograms → explicit bounds in SECONDS with **11 explicitBounds
  and 12 bucketCounts** (the fact-check's medium fix — BUCKETS_MS has 11
  finite bounds, `prometheus.rs:53-55`; OTLP bucket counts are per-bucket
  DELTAS, differenced against PromState's cumulative buckets).
- Failure isolation: cumulative temporality means every interval re-sends
  the full state — a failed POST is NOT retried (nothing is lost; the next
  interval re-sends) and failure logging is throttled. Dedicated reqwest
  client with an explicit timeout (in-repo precedent: the control CLI
  client's 3s/5s, `control/mod.rs:85-91`). Zero new hooks on the
  `/v1/messages` path; a test asserts proxy behavior is identical with
  OTLP on/off.
- Metrics-only. Traces are explicitly out (§4): they would need new JSONL
  fields, a bounded queue with real drop semantics, and duplicate what
  `decisions.jsonl` already persists.

## 4. Non-goals (v0.5 IS NOT)

- runtime adaptive routing (in-memory derived cost blended into scores,
  EWMA or window-fold) — advise-only first; the runtime variant is a
  follow-up only after advise proves the signal's value (§11)
- price auto-discovery, bill-truth claims — prices stay hand-entered facts
  (`config.rs:113-115`); the V0.4 §4 boundary carries forward verbatim
- quality_weight derivation — no honest path exists (§3.1)
- client-side stable session ids (`x-ccm-session`, per-project default
  ids) — `--client` is the stable-id story; proxy-side persistence is the
  shipped half (§3.2)
- OpenAI-side endpoint expansion (embeddings, images, audio, files,
  rerank, legacy completions) — no client ever sends those to the proxy
- OTLP traces/logs signal, exemplars, delta temporality; protobuf encoding
  (JSON is first-class on the same collector port)
- capability-probe results or context windows persisted into the Model
  schema — point-in-time facts go stale in config
- one-step `discover` registration of brand-new providers (network probes
  stay out of the local write path; the three-step flow is reused)
- remote control authentication (deferred, unchanged — design first)
- reverse translation (OpenAI-native clients → CCM), UI/TUI
- macOS (re-entry criteria unchanged, V0.3_PLAN §3)

### M0 — external verification spike

Days, not weeks; ships nothing. The only acceptance items the repo's test
suite cannot express; results recorded in this file when done (the V0.4 M4
E2E precedent). Four gates:

1. One live `ccm run --proxy` session with the proxy's stderr log and a
   scratch `CCM_HOME`: does the installed Claude Code call `POST
   /v1/messages/count_tokens` through `ANTHROPIC_BASE_URL`? What degrades
   on the 404 (local estimate vs error)? Does it call `GET /v1/models` at
   all? — gates M3's premise and its Option D entirely.
2. Gateway calibration: do z.ai / minimax (the configured
   anthropic-compatible providers) expose `GET /v1/models`, with what
   response shape and auth? — gates M5's premise and calibrates the
   parser's looseness. If they broadly lack it, M5 shrinks to doctor's
   existence line + honest docs and M6 is dropped.
3. Owner pipeline facts for OTLP: collector present? auth needed?
   protobuf-only receivers (one would reopen §3.5's option A)? interval
   habit? — gates M4's parameters.
4. otelcol smoke harness identified (a local collector run for M4's
   acceptance; not CI).

Landed record (2026-10-09, Windows, claude 2.x via the exact
`run_claude_via_proxy` env contract — ANTHROPIC_BASE_URL/MODEL/AUTH_TOKEN
placeholder + x-ccm-client header — against an instrumented proxy build
with a fallback path logger, scratch `CCM_HOME`, real z.ai upstream; no
committed source change):

- **count_tokens: CONFIRMED, near-window only.** Small prompts (1
  `/v1/messages` call) and ~110k-token inputs generate zero count calls;
  at ~140k tokens Claude Code bursts `POST /v1/messages/count_tokens
  ?beta=true` (query string rides the path; route matching ignores it),
  tolerates the 404s, falls back to its local estimate, and the send
  succeeds. At ~190k estimated tokens it retried count_tokens **17 times**
  (all 404), then refused locally — "Prompt is too long", exit 1, the
  message never sent. So the 404 today costs a ~17-request retry burst on
  every near-window send, and near-window prompts that would fit the real
  tokenizer are refused on a local estimate. M3's premise is real and the
  pain is sharper than the plan assumed.
- **`GET /v1/models`: never called** across all observed flows (small,
  large, `/context`, near-window). Option D is DROPPED by its own gate;
  the 404 stays and USAGE says so.
- **`HEAD /api/hello`: new endpoint fact.** Claude Code probes the base
  URL with HEAD /api/hello at session start; the 404 is tolerated (every
  session proceeded). Documented, no action.
- Cosmetic: claude warns `[claude-code:unrecognized_model] {"model":"ccm"}`
  on the placeholder model name and proceeds — known v0.4 behavior,
  unchanged.
- **Gate 2 — both gateways implement `GET /v1/models`** (200, x-api-key +
  anthropic-version: z.ai 11 models `glm-4.5`…`glm-5.3-flashx` with
  `data[].{id,type,display_name,created_at}` and NO has_more/first_id/
  last_id fields at all; minimax 8 models with the FULL anthropic list
  shape — has_more=false, first_id, last_id). Neither carries
  capabilities/max_input_tokens (as predicted: capability data is
  genuine-Anthropic-only). Both configured model_ids are present. M5's
  premise holds on the exact gateway class it worried about, and the
  parser must treat pagination fields as OPTIONAL (z.ai omits them).
  Genuine Anthropic not probed (no stored credential — the provider is
  dormant in this config).
- **count_tokens upstream reality (M3 design input): z.ai's
  count_tokens is a STUB** — `{"input_tokens":0}` for any input,
  including 12,800 chars; **minimax counts for real** (2,564 tokens for
  the same input). Passthrough therefore means z.ai-routed clients get
  count=0 (Claude Code reads "context empty": never compacts, never
  refuses early, overflow surfaces at send time) while today's 404 makes
  it fall back to a local estimate. A zero count is also legal for empty
  input, so the proxy cannot distinguish stub from truth — M3 documents
  this boundary (the gateway's answer is the answer) and considers a
  warn-once stderr line for count==0 against a large request body.
- **Gate 3 — no local collector** (4317/4318 unbound, no collector
  processes). M4 proceeds on defaults: loopback 4318, no auth, 30s
  interval; the push path is ready for whenever a collector appears.
- **Gate 4 — docker 29.7.2 available**: M4's smoke runs
  `otel/opentelemetry-collector` as a local container with a file
  exporter; not CI.

### M1 — `ccm advise`

- §3.1 in full: `src/advise.rs` pure derivation + top-level CLI, recompute
  fold (tokens × current pricing), min-samples 20, window 7d default,
  three-way table + pasteable TOML + tokenizer caveat, never writes config.
- Acceptance: existing suite green with `select.rs`/`proxy.rs` zero-diff

## 6. Sequencing rationale and hot-zone rules

Order: M0 → M1 → M2 → M3 → M4 → M5 → (M6) → M7. M4 is logically
independent of M2/M3 (disjoint files except serve()/api.rs wiring) and may
swap with M3 if the owner's collector need is the more urgent value.

The order is value-first with the external risks retired early:

1. M0 first: the only items unit tests cannot cover. Two milestones (M3's
   premise, M5's premise) are scoped on its answers; a bad result (e.g.
   Claude Code hard-errors on count_tokens 404, or the gateway class
   lacks /v1/models) must be discovered before dependent design freezes.
2. M1 second: cheapest (S), zero routing risk, immediate value from
   existing usage.jsonl — and every week it exists earlier is another week
   of advice history. It also forces the pricing-recompute primitive
   early, which M5's pricing skeleton references.
3. M2 third: the worst silent misbehavior on the list (post-restart
   wrong-model routing with no error); fully self-contained; lands the
   ClientEntry counter/last_seen semantics decision that M3 consumes.
4. M3 fourth: consumes M2's decided counter semantics; gated on M0's E2E.
5. M4/M5: externally calibrated by M0; M5 has the largest new surface
   (CLI flow + config schema) and no proxy-path risk, so it lands last
   among features.

Hard rules (mirroring V0.4's hot-zone discipline):

- Only ONE theme edits proxy.rs's `serve()`/`forward()` cut points at a
  time: M2 takes serve() + apply_switch; M3 takes the router + a dispatch
  path; M4 takes serve() wiring + the PromState gate. Serialize M2 → M3 →
  M4.
- Background-task convention, stated ONCE and followed by all new loops
  (clients refresh, OTLP push; template = the metrics-snapshot task,
  `proxy.rs:166-184`): spawn in serve(), config read once at startup,
  idle-skip, explicit client timeout, throttled warn-on-failure, no
  exit-time claims.
- Config placement convention: runtime/routing state at top level
  (`[clients]`); telemetry under `[observability]` (`[observability.otlp]`).
  Every new section: serde defaults + validate + examples/config.toml in
  the same change.
- The two-proxy / one-CCM_HOME boundary is stated ONCE, consolidated, with
  the history single-writer rule: three files, three answers —
  `history/.lock` (OS lock, second proxy degrades), `state.toml` (no lock,
  no proxy writer), `clients.toml` (no lock, last-writer-wins clobber).
- One docs work item per milestone + one final consistency pass in M7 (the
  five themes collectively touch USAGE throughout, DESIGN §8/§13/§18.5/§19,
  and supersede V0.4_PLAN lines 225-226, 230-232, §10:696, §11:704-708).
- Every milestone lands independently green, one issue per commit, CI
  green on every push to main.
