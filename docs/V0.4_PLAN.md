# CCM v0.4 Plan

## 1. Purpose

This document is the operational plan for CCM v0.4. It mirrors the structure
of `docs/V0.3_PLAN.md`: scope boundaries, explicit non-goals, milestones,
risks, and owner decisions.

Read in this order:

1. `README.md`
2. `docs/DESIGN.md`
3. `docs/V0.3_PLAN.md` (esp. sections 16–17)
4. this file

Provenance: the three theme designs, the milestone roadmap, and an adversarial
verification pass were produced on 2026-10-03 by a 5-agent design workflow
(3 designers + 1 synthesizer + 1 adversarial verifier). The verifier confirmed
the sequencing logic and all ~25 cited code touch points against the tree;
its 6 must-fix corrections are already folded into the milestones below
(section 7). Do not re-litigate settled decisions — see section 8.

## 2. Status

**Underway** (2026-10-03): M0 (proxy split), M1 (translation engine), M2
(openai-compatible wiring), M3 (multi-client core), M4 (multi-client
launcher/CLI/doctor, E2E accepted), and M5 (history store: engine, config,
proxy wiring, disk-backed decision queries, `ccm history` CLI, doctor
check) have landed on main; M6 (usage capture + cost accounting) is next.
v0.3.0 is released and the CI gate must stay green on every push to main
while v0.4 work lands.

Owner theme selection (2026-10-03):

- multi-client routing — per-session runtime targets inside one proxy
- OpenAI adapter — upstream-side protocol translation
- observability persistence — history, real cost accounting, `/metrics`

Explicitly deferred (not selected): remote control authentication, UI/TUI.

## 3. Themes

### 3.1 Multi-client routing

Problem: one `ccm proxy` holds one runtime target
(`ProxyState.target`, `src/proxy.rs:44`); `control_switch` is a global write
and `ccm run --proxy <target>` does a global pre-switch (`src/main.rs:120-124`)
— two terminals on one proxy cut each other over. The only workaround today
is USAGE §4.6's dual-proxy dual-port setup, which duplicates circuits,
metrics, and decisions.

Mechanism:

- Client identity, two channels, both launcher-injected, never in any file:
  1. Primary: `ANTHROPIC_CUSTOM_HEADERS="x-ccm-client: <id>"` — official
     Claude Code env var (requires claude ≥ v2.1.227). If the parent
     environment already sets the variable, append a line; never clobber.
  2. Fallback (version-independent): the placeholder token becomes
     `ccm-local-<id>` (was fixed `ccm-local`); the proxy parses the id out of
     the inbound `Authorization` header before stripping it.
- `ProxyState.clients: HashMap<String, ClientEntry>` with
  `ClientEntry { target, requests, last_seen_ms }` — in-memory only, cleared
  on proxy restart. The global `target` remains the default.
- Per-request target resolution: id with entry → entry target; id without
  entry → follows global (decided, §8.1); no id → global, byte-identical to
  v0.3.
- `x-ccm-client` MUST be added to the `copy_request_headers` strip list
  (`src/proxy.rs:1176-1187` forwards unknown headers upstream today — without
  the strip, local identity leaks to providers).
- Switch scoping, three layers, all runtime-only (invariant 8):
  `ccm switch <t> [--client <id>] [--global]`, resolution order
  `--client` > `CCM_CLIENT_ID` env > global. The `/switch` skill needs zero
  changes — it inherits `CCM_CLIENT_ID`. `ccm run --proxy <t> --client <id>`
  does a scoped pre-switch (fixes the `main.rs:120-124` crosstalk; decided
  strict client-scoped, §8.1). `ccm use` is untouched (invariant 9).
- API: `POST /_ccm/switch/{t}?client=<id>` (invalid id charset → 400; valid
  charset `[A-Za-z0-9._-]{1,64}`), new `GET /_ccm/clients`, `?client=`
  filters on status/traces/decisions.
- Circuits and metrics stay model-scoped and shared (invariant 2): a model
  failing for client A is failing for everyone (same upstream, same
  credential); a retry-storming client opening a circuit affects others —
  that correctly reflects upstream health.
- `RoutingDecision` / `AttemptTrace` gain `client: Option<String>`
  (additive serde).
- doctor: extend the settings-override check with `ANTHROPIC_CUSTOM_HEADERS`,
  capture `claude --version`, warn < 2.1.227 → token channel only.
- Client id is NOT authentication — any local process can forge it. Same
  trust domain as the unauthenticated control API; document explicitly.

### 3.2 OpenAI adapter (provider kind `openai-compatible`)

Problem: CCM speaks Anthropic `/v1/messages` on both sides, so v0.3 only
routes to Anthropic-format gateways. Many gateways — DeepSeek, SiliconFlow,
Moonshot, OneAPI/new-api aggregators — only expose OpenAI-format
`/v1/chat/completions`.

Mechanism:

- New `ProviderKind::OpenAICompatible` (TOML value `openai-compatible`,
  kebab-case; enum variant addition does not break old configs). Upstream
  path `/v1/chat/completions`. Client side stays Anthropic — translation is
  upstream-side only.
- Auth (decided, §8.1): `Provider.auth` becomes `Option<ProviderAuth>` +
  `resolved_auth()` — anthropic kinds default `x-api-key` (unchanged),
  openai-compatible defaults `bearer`; explicit override still wins. Exactly
  one upstream credential header, as today.
- New module `src/translate.rs`: pure functions + an explicit SSE state
  machine. No OpenAI SDK.
- Request translation is field-by-field explicit construction; anything not
  listed is dropped by construction (honest default). Mapped: `system` →
  system message; `tool_use` → `tool_calls`; `tool_result` → `role:"tool"`
  messages; `tool_choice` four states; `stop_sequences` → `stop` (truncate to
  4, warn); base64 `image` → `image_url` (best-effort); adjacent same-role
  text merge (many gateways 400 on non-alternating roles).
- Dropped with a once-per-process warning (OnceLock) and documented:
  `cache_control` (requests via this kind get NO prompt-cache benefit — a
  cost, must be stated in docs, not footnoted), `thinking` blocks, `top_k`,
  unknown fields.
- Token limit: send `max_tokens` only (decided, §8.1). `stream: true`
  additionally injects `stream_options: {"include_usage": true}`.
- Non-stream response: `choices[0]` / `finish_reason` → `stop_reason` full
  table; usage mapping; `msg_`-prefixed id skeleton.
- Stream translation: incremental buffering split on blank lines, 1 MiB
  per-event cap; text block lazy-open; tool_calls opened/closed by index
  order (interleaved index deltas have defined behavior + tests);
  `message_start` carries `usage.input_tokens: 0` (honest placeholder — real
  usage rides `message_delta` from the final usage frame); `[DONE]`/EOF →
  synthesized closing events; bad frame or mid-stream break → `error` event
  then close, NEVER a faked clean `message_stop`.
- Usage mapping includes cached tokens:
  `prompt_tokens_details.cached_tokens` (DeepSeek:
  `prompt_cache_hit_tokens`) → `cache_read_input_tokens`, priced at the
  cache_read rate. Without this, automatic context caching on DeepSeek would
  silently bill cache hits at full input price.
- Terminal (non-fallback) OpenAI error bodies are translated to the
  Anthropic error envelope; status code preserved.
- Fallback semantics unchanged (status-code based, `proxy.rs:1140`);
  mixed-protocol routes and fallback work naturally (openai primary →
  anthropic fallback). Commit point remains response-header acceptance;
  translation failure never triggers mid-stream failover (invariant 5).
- Translation failure before send rides the existing resolve-error path
  (HALF_OPEN probe slot release semantics preserved).

### 3.3 Observability persistence

Problem: all v0.3 observables — decision ring, trace ring, per-model metrics,
circuit state — are in-memory and die with the proxy (`DESIGN.md` §18.4
design debt). Nothing exports to monitoring. `cost_weight` is a hand-entered
relative number; there is no token-based cost accounting.

Mechanism (one skeleton, three sub-features):

- Storage: append-only JSONL + rotation in `$CCM_HOME/history/` —
  `decisions/usage/metrics/circuit.jsonl`. Rejected alternatives: rusqlite
  (C build dependency + WAL side files, breaks the pure-Rust tree stance),
  redb (+~30 transitive deps for B-tree features a linear time-window scan
  never uses). A `HistoryReader` trait keeps the engine swappable. Rotation:
  ≥50k records or ≥8 MiB per file; retention 14 days by mtime (defaults,
  configurable). Torn tail lines are skipped (documented).
- Single-writer rule: two `ccm proxy` processes sharing one `CCM_HOME`
  (exactly today's USAGE §4.6 workaround) must not silently interleave
  writes or duplicate decision ids. Lock or per-instance namespacing, or at
  minimum detect-and-warn plus a documented single-proxy-per-CCM_HOME
  assumption. Decide during M5; do not ship default-on history without it.
- Write path: tokio mpsc bounded channel (capacity 1024) + writer task
  (`recv_many` batching, BufWriter, flush per batch). Producers always
  `try_send` — a full queue drops and counts, never blocks `/v1/messages`.
  Observability failure must not affect routing. No exit-time final snapshot
  is claimed (the proxy has no graceful shutdown); periodic 30s metrics
  snapshots + torn-tail tolerance cover the gap.
- `decision_seq` recovers from the tail file at startup (ids globally
  unique); runtime metrics restart from zero (stale snapshots would distort
  healthiest/weighted ordering — history queries go to disk instead).
- Usage capture: wrap only accepted 2xx responses at the unified response
  dispatch point (which M2 created) with an incremental scanning stream —
  SSE line scanner (BytesMut tail buffer capped at 64 KiB, cheap substring
  pre-check before serde) or incremental JSON scan by response content-type.
  Input/cache tokens come from `message_start` but are MERGED from
  `message_delta.usage` when present (translated streams carry real usage
  there). Emits one `UsageRecord` per decision on stream end or scanner Drop
  (client disconnect → `complete: false`). Zero new direct dependencies: a
  generic wrapper over `futures_core::Stream` (already in-tree via
  axum/reqwest). `proxy_response` signature changes exactly once, here
  (+model, decision_id, pricing).
- Cost accounting: `[models.<name>.pricing]` hand-entered per-MTok prices
  (input / output / cache_read / cache_write); missing table → recorded as
  unpriced (never guessed). `cost_usd = Σ tokens/1e6 × price` with the price
  snapshot stored in the record. `cost_weight` keeps its routing-weight
  semantics — no linkage.
- Prometheus `/metrics` on the SAME listener (the loopback guard already
  covers it; no second port), hand-rendered text format (~150 lines, no
  prometheus crate). Families: `ccm_proxy_requests_total{target,outcome}`,
  `ccm_attempts_total{model,outcome}`, latency dual-track (new fixed-bucket
  histogram for cross-restart `histogram_quantile` + keep the EWMA gauge),
  `ccm_decision_duration_seconds{target}`, `ccm_circuit_open` /
  `ccm_circuit_consecutive_failures`, `ccm_tokens_total{model,kind}`,
  `ccm_cost_micro_usd_total{model}` (integer micro-USD),
  `ccm_history_dropped_total`, `ccm_up` / process start time.
- Config: `[observability]` section, all serde defaults — old configs
  unchanged, `history_enabled = true`, `prometheus_enabled = true`.
- API: `/_ccm/decisions?since=&until=&model=` (no params = current in-memory
  behavior, fully compatible), new `/_ccm/usage`, `/_ccm/cost?day=`.
- CLI: `ccm history decisions|metrics|circuit|cost` — offline reads, works
  with the proxy stopped. `ccm doctor` gains a history-directory check.

## 4. Non-goals (v0.4 IS NOT)

- reverse translation (OpenAI-native clients such as Codex → CCM)
- any authentication or remote/LAN binding — loopback-only unchanged; client
  id is identity, not a security boundary (forgeable by local processes)
- per-client credentials, per-client providers, per-client circuits,
  per-client metrics, or per-client target persistence (`state.toml` still
  holds only `current`)
- prompt-caching or extended-thinking fidelity via openai-compatible
  (`cache_control` / `thinking` stripped and documented; no cache discount
  is a known cost of that kind)
- mid-stream failover — translation failure and truncated streams terminate
  the stream, never switch models
- price auto-discovery, bill-truth claims, adaptive routing, cost_weight
  auto-derivation
- multi-instance aggregation, OTLP export, dashboards, UI/TUI
- private per-gateway parameter shims (`enable_thinking` etc.) unless a
  core-MVP gateway hard-blocks on one
- non-chat-completion endpoints (embeddings, models list, images, audio,
  files, rerank, legacy completions); `count_tokens` stays unforwarded
  (existing behavior)
- macOS (still not claimed; re-entry criteria in V0.3_PLAN §3)

### M0 — proxy.rs module split

- Behavior-preserving mechanical split per DESIGN §18.1: decision/trace rings
  → `routing/decision.rs`, ModelMetrics + EWMA → `routing/metrics.rs`,
  circuit state → `routing/circuit.rs`, control handlers + Router →
  `control/api.rs`. `forward()` and the HTTP layer stay in the proxy core.
- `forward()` itself remains ONE function that all three themes edit — M0
  reduces, but does not eliminate, the hotspot. Strict serialization
  (section 6) is the actual mitigation.
- Acceptance: existing tests byte-identical (not a frozen count — parallel
  M1 merges add tests), four-check gate green, zero behavior change.
  Separate commit(s) from any feature work.

### M1 — translate.rs engine

- All of §3.2's translation logic as pure functions + the SSE state machine,
  in one new file with zero dependencies on existing proxy code. Mergeable
  independently; exposes no user behavior until M2.
- Tests self-contained in the module: table-driven field mappings;
  arbitrary byte-offset chunking (UTF-8 multibyte and blank-line separators
  across chunk boundaries); interleaved/out-of-order tool_call index deltas;
  argument deltas concatenating to valid JSON; cached-token usage mapping.

### M4 — multi-client launcher/CLI/doctor

- `run_claude_via_proxy` takes a client id; inject `CCM_CLIENT_ID`, append
  `ANTHROPIC_CUSTOM_HEADERS`, placeholder token `ccm-local-<id>`;
  `ccm switch --client/--global`; `ccm run --client` (default: short random
  id — PID + start-millisecond hash truncated to 8 hex, zero new deps);
  `control.rs` switch passes `?client=`; `integrate.rs` SKILL.md text only;
  doctor extensions (§3.1).
- Append guard (from M3 verify): when the parent environment already sets
  `ANTHROPIC_CUSTOM_HEADERS`, check for an existing `x-ccm-client` line
  before appending — the proxy reads only the FIRST header value
  (`client_id_from_headers`), so two lines with different ids would resolve
  unpredictably. Same-id duplication is harmless.
- Direct-launch guard (found in the M2 doc pass): `ccm run <target>`
  WITHOUT `--proxy` against an openai-compatible model must fail fast with
  a clear message — translation exists only in the proxy, so a direct
  launch would send Anthropic protocol to an OpenAI endpoint. `ccm doctor`
  reports the same hint for openai-kind current targets.
- Manual E2E acceptance (the only part the repo cannot test; record results
  here): (a) `ccm run --client X` with claude ≥ 2.1.227 → `/_ccm/clients`
  shows X via header channel; (b) without custom-header support → token
  channel resolves the same id; (c) legacy `ccm-local` token (a v0.3-launched
  session) → treated as no-id → global.
- E2E results (2026-10-03, Windows, claude 2.1.261, build at the M4 fix
  commit, scratch `CCM_HOME`, upstream pointed at a refusing loopback port —
  no real credentials or providers involved):
  - (a) **pass** — `ccm switch <t> --client e2ea` then `ccm run --proxy
    --client e2ea` with a piped prompt: real claude made 9 requests through
    the proxy; every `/_ccm/decisions` record carries `client=e2ea` and
    `/_ccm/clients` shows the entry with `requests=9`.
  - (b) **pass (raw-HTTP variant)** — `Authorization: Bearer ccm-local-e2eb`
    with no custom header attributed to `client=e2eb`. The real-claude
    variant needs a claude install older than 2.1.227 (not available here);
    the channel is a plain Authorization header on the wire, which the raw
    request exercises exactly as an old client would send it.
  - (c) **pass** — bare `Bearer ccm-local` attributed to no id (decision
    `client` absent), following the global target.
- Docs: USAGE §4.6 rewritten from dual-proxy to single-proxy per-client;
  DESIGN §13 endpoint table + §19 annotations (client id is not
  authentication).

### M5 — history store

- §3.3 storage: JSONL + rotation + retention, `[observability]` config,
  writer task with `try_send` hooks at `store_decision` (×4 call sites),
  `record_*` (×4), circuit transitions (OPEN/HALF_OPEN/CLOSED with reason);
  decision_seq recovery; single-writer rule decided and implemented; NO
  exit-final-snapshot claim.
- `?since/?until/?model=` on decisions; `ccm history decisions|metrics|circuit`;
  doctor history check. `state.toml` untouched.
- Tests: rotation/retention/torn-tail skip; persisted lines contain no
  credential material (assert no known-token substring); channel-full does
  not block requests.
- Landed (2026-10-03): engine + `[observability]` config + proxy wiring in
  one commit (engine alone fails clippy dead_code; deviation from
  one-issue-per-commit, accepted and documented there), then disk-backed
  `/_ccm/decisions` params, the `ccm history` CLI, and the doctor line as
  separate commits. 97 tests green, including a fifth env-serialized
  integration test pinning the JSONL contract end-to-end and the exact
  key whitelist of a persisted decision line.
- As-built deviations from the §3.3 sketch (accepted, recorded here):
  - Write path is `std::sync::mpsc::SyncSender` + a dedicated std thread,
    not tokio mpsc + a writer task. Same bounded-1024, always-`try_send`
    semantics; the std thread buys zero async-runtime IO in the writer,
    `recv_timeout` as the natural poll point, and a deterministic drop-join
    (`Drop for HistoryInner` drains, flushes, and joins the writer when the
    last handle goes away — a normal `main` return therefore persists
    everything in flight; a killed process still skips it, as §3.3 assumed).
  - Single-writer rule = an OS file lock (`File::try_lock`) on
    `history/.lock`, held for the process lifetime and kernel-released on
    death (no stale-lock recovery). A second proxy on one CCM_HOME keeps
    routing but runs with history disabled plus one warning.
  - Files are `decisions/metrics/circuit.jsonl` today; `usage.jsonl`
    joins in M6 as planned.

  scanner tolerates message_start without a usage field (the v0.3 mock does

## 6. Sequencing rationale and hot-zone rules

Order: M0 → (M1 in parallel with M0) → M2 → M3 → M4 → M5 → M6 → M7 → M8.
M4 and M5 may run in parallel (nearly disjoint files).

The order is physical-conflict analysis over the shared hot spots, not theme
priority:

1. M0 first (backlog item 1): all three themes edit proxy.rs (1641 lines);
   the split turns most collisions into independent module edits.
2. OpenAI second: deepest surgery on the forwarding path, so it lands on the
   cleanest post-split code; highest external uncertainty (real gateway
   behavior), so earliest merge buys the longest soak time; its engine (M1)
   is a pure new file that parallelizes with M0. Critically, M2 creates the
   unified response dispatch point (`proxy_response` | `translate_response`)
   so M6 wraps the usage scanner once, covering native and translated
   streams.
3. Multi-client third: mostly control-plane + launcher work, but its
   `client` field must precede M5's JSONL schema freeze, and it upgrades
   observability's per-session cost attribution from out-of-scope to nearly
   free.
4. Observability last: it hooks every terminal point (store_decision ×4,
   record_* ×4, circuit ×2) and changes `proxy_response`'s signature — going
   last means each hook is written once against the final v0.4 surface.

Hard rules:

- `forward()` is the one function all three themes edit — never two themes
  editing it in flight simultaneously.
- `proxy_response()` signature changes only in M6.
- `copy_request_headers`' strip list is touched twice (x-ccm-client in M3 —
  REQUIRED, prevents local identity leaking upstream; anthropic-version in
  M2, optional) — each change carries its own test.
- RoutingDecision schema evolves additively in M3, BEFORE M5 serializes it.
- Every milestone lands independently green (unit or mock-integration
  evidence), one issue per commit, CI green on every push to main.

## 7. Verification corrections already folded in

The adversarial verify pass confirmed the roadmap's sequencing and code
citations, and found 6 must-fix items — all folded into the milestones above:

1. Usage scanner must merge input/cache tokens from `message_delta.usage`
   when present (translated streams carry real usage there; message_start is
   zeroed by the translator) — else every openai-kind request silently
   records input/cache = 0. (M6, §3.3)
2. OpenAI cached tokens (`prompt_tokens_details.cached_tokens`, DeepSeek
   `prompt_cache_hit_tokens`) must map to `cache_read_input_tokens` at the
   cache_read rate — else DeepSeek's automatic caching silently bills full
   input price. (M1, §3.2)
3. History needs a single-writer story for shared `CCM_HOME` (two proxies =
  today's documented workaround) — concurrent append + duplicate
  decision_seq otherwise. (M5, §3.3)
4. The client-identity channel needs real E2E acceptance (3 runs, M4) — the
  repo cannot test it; both channels are officially documented, no spike
  needed.
5. The tokio-stream dependency claim was factually wrong (zero matches in
  Cargo.lock) — replaced with a futures_core::Stream generic wrapper: zero
  new dependencies. (M6)
6. The "final snapshot on exit" claim required graceful shutdown the proxy
  does not have — dropped. (M5)

Minor corrections also applied: `record_*` is 4 functions (not 5); M0
acceptance says "existing tests byte-identical" (not a frozen count); M4's
file list includes `control.rs`; M1 defines interleaved tool_call index
behavior; Windows rotation closes-before-rename inside the single-owner
writer task.

## 8. Owner decisions

### 8.1 Decided (2026-10-03, owner)

1. **openai-compatible auth default**: kind-inferred default — anthropic
   kinds keep `x-api-key` (unchanged), openai-compatible defaults `bearer`,
   explicit override always allowed. Invariant 7 is read as "at most one
   upstream credential header, with documented per-kind defaults" (note:
   `Provider.auth` already serde-defaulted to `x-api-key`, so strict
   explicitness was already softened).
2. **Un-switched clients follow the global target** until their first scoped
   switch (no lazy materialization).
3. **`ccm run --proxy <target>` pre-switch is strictly client-scoped**,
   never writes global.
4. **OpenAI token-limit field: send `max_tokens` only**; revisit only if a
   real gateway rejects it.

### 8.2 Registered defaults (execute per proposal; speak up before the milestone starts)

Multi-client: keep the token fallback channel (`ccm-local-<id>`); default
client id is short-random per launch (no cross-restart session identity —
that is a v0.5 question, `x-ccm-session`); client entry whose target no
longer resolves → error (visible, same failure mode as global target today);
decisions/traces keep the shared ring + `?client=` filter (per-client rings
or LRU eviction only if contention shows up); `/_ccm/status` default shape
unchanged; add a minimal `ccm clients` CLI listing.

behind a per-provider flag later); terminal error bodies translated to the
Anthropic envelope; non-stream translation failure does NOT retry (commit
