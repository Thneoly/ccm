## 10. Security Review Before Release

### Loopback-only Proxy — DECIDED and implemented (2026-10-02)

The Control API is unauthenticated, so a Proxy bound to `0.0.0.0:<port>` would
expose upstream proxy capability and runtime switching to the network.

v0.3 behavior, now implemented:

> `ccm proxy` rejects non-loopback bind addresses before loading configuration
> or opening the listener.

LAN/remote access intentionally remains unsupported; design authentication
first (v0.4 backlog: remote control authentication).

## 11. Known Technical Risks

### 11.1 Large proxy module

`src/proxy.rs` is large.

Do not refactor purely for cleanliness during release stabilization.

Only split if required to fix real correctness/testability problems.

### 11.2 Integration test environment variables

The Mock Provider test mutates process environment:

- `CCM_HOME`
- `CCM_PRIMARY_API_KEY`
- `CCM_FALLBACK_API_KEY`

It currently uses one async integration-style test to avoid internal parallel races.

If future tests add more environment mutation, introduce explicit serialization or isolate test processes.

### 11.3 Keyring dependency features

Keyring features are target-specific in `Cargo.toml`.

If any target fails to compile, verify the keyring feature set against the actual resolved keyring crate version before changing application code.

### 11.4 Linux headless keyring

Native keyring may not be usable in minimal containers.

This is expected; environment credentials are the supported headless path.

### 11.5 Route update semantics

Re-running `ccm add route` may overwrite policy fields with CLI defaults.

Do not block v0.3 on redesign unless tests expose a real user-facing regression.
